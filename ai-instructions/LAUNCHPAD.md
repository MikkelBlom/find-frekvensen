"Find Frekvensen" — an interactive drop-in station for Ada Lovelace Day at Coding Pirates Odense (12 Oct 2026). Each child holds a micro:bit and tilts it to sweep a needle across a retro radio dial on a big TV, hunting hidden signals by strength, holding to lock them, and collecting a secret message; the harder levels make the signal move, echoing Hedy Lamarr's frequency hopping. 4–8 (up to 10) kids play at once, each with their own field on screen. Handheld micro:bits transmit over radio to a base-station micro:bit on USB, which feeds a Next.js 16 app over Web Serial. The firmware is deliberately dumb (it only reports needle position) so all game logic lives in the app, which also means the whole game runs in a built-in simulator with no hardware. Ships as a portable offline Electron .exe for the venue PC.

## Notes

### Hard invariants — do not violate `#1` 📌  [architecture]
1. The firmware stays dumb. A handheld only reports its own needle position; every station, decoy, lock rule, movement and message lives in the web app. This is why puzzles can change without re-flashing 10 micro:bits.
2. The whole game must run in the simulator with no hardware. The simulator and the serial reader both write into the same devices map that the engine reads — they are interchangeable. Never add logic that only works with real serial.
3. Offline on the day. No runtime network calls, no next/font/google, no CDNs. Inline SVG, WebAudio synth, system fonts.
4. Sound is a pure plus. Fully playable and legible with sound off; never gate progress or feedback on audio.
5. The debug panel must hide completely (press d) so children never see operator controls.
6. Chrome/Edge only (Web Serial), designed for a bright room and a TV seen from 1.5–2 m: big type, strong contrast, uniform fields.

### Serial-port contention — the bug that cost a session `#3`  [gotcha, hardware]
Symptom: one handheld spawns dozens of phantom players, needles drift on their own, the error count climbs, the real device flickers in and out.

Cause, confirmed on hardware 2026-07-23: TWO PROGRAMS READING THE SAME SERIAL PORT. The MakeCode editor was still connected to the base station while the web app was reading it; they split the byte stream and both got shredded. Closing MakeCode fixed it instantly.

The earlier theory — "micro:bit V1 drops bytes at 115200" — was wrong. A lone V1 at 115200 is clean. Do not drop the baud to "fix" noise; at 9600 the link cannot carry 8–10 handhelds.

### Serial protocol contract — the two checksums must stay identical `#4`  [architecture, firmware]
Line format: R,<id>|<pos>|<flags>|<checksum>\n at 115200 baud.
- id = hardware serial, abs % 1_000_000 (short, so fewer bytes on the wire)
- pos = 0–1000
- flags = bitmask (bit0 = A, bit1 = B)
- checksum = rolling hash h = (h*31 + c) % 10000 over "<id>|<pos>|<flags>"

parseLine requires exactly four all-digit fields AND a matching checksum, otherwise the line is dropped and counted as a parse error. That gate is what turns corruption into a harmless dropped packet instead of a phantom player — verified against every single-byte deletion from the real hardware logs, zero false accepts.

The checksum() in firmware/receiver.js and the one in src/serial/protocol.ts must stay byte-identical. Change one, change both, and re-flash every handheld — micro:bit radio strings also cap at 19 bytes, so the format cannot grow much.

### Difficulty ladder as it stands `#6`  [gameplay]
Each field climbs the ladder independently; a new device starts at green and advances one step per completion, capped at red.

Green — 3 letters (ADA), stationary stations, full directional arrow hint from warmth 0.45.
Yellow — 4 letters (HEDY), signal MOVES at 110 units/s across a 58-wide window, full arrow hint.
Red — 5 letters (GRACE), moves at 135 units/s across a 50-wide window, hint only from warmth 0.8 (nearly on top of it).

Speeds and window widths are deliberately set so dwell time (width ÷ speed) is shorter than the required hold — 0.53 s vs 0.65 s on yellow, 0.37 s vs 0.62 s on red — meaning a still needle can never catch a moving signal. You have to follow it. Verified: standing still on red for 10 s captures nothing.

Also: the signal bar only tops out and the dial only goes fully sharp/green when the needle is genuinely inside a lock window. Warm-but-not-capturable stays visibly fuzzy with a capped bar — an earlier version looked "done" while still far out.

### Engine / React split — keep the fast loop out of React `#7`  [architecture]
src/game/engine.ts is plain imperative TypeScript running one loop. It owns everything per-frame (needle, warmth, noise) and draws straight to canvas; only low-rate snapshots go into the Zustand store for the React chrome (titles, letters, banners). Never push needle or warmth values through React.

Supporting details: the loop also runs a setInterval fallback that steps frames only when document.hidden, because browsers pause requestAnimationFrame on hidden tabs (this made the engine look dead in a preview and would bite a minimised kiosk). The static dial is rendered once per size into an offscreen canvas and blitted each frame. Fields use container queries and cqmin units so the same layout works at 1–10 fields and at 1080p or 4K with no media queries.

All colours and sizes live in src/game/tokens.ts and src/game/palette.ts — re-theme there, not in components.
